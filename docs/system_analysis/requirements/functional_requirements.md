# AquaPredict LIMS — Функциональные требования (Functional Requirements)

**Версия:** 1.0-черновик. **Статус:** детализация Волны 2 выполнена (C-02); на ревью ведущему (Gate 2).
**Архитектурное направление — вариант A (надстройка), ПОДТВЕРЖДЁН ведущим 2026-10-12 (Gate 1):** AquaPredict — предиктивная надстройка над «БИТ.Лаборатория», а не самостоятельный LIMS. Партии, пробы, результаты, протоколы, задачи и ЭП живут в 1С; AquaPredict читает их по OData, пишет задачи/рекомендации через HTTP-сервис и добавляет предиктивный контур. **Выполнено ведущим (см. `change_log.md`):** правка In-Scope в `01_vision_and_scope.md`, пересмотр UC5, backfill журнала, переформулировка LGL-01.
**Основа:** базис `01…10`, LGL-01…14, KPI (`kpi.md`), NFR-1…7, параметры (`requirements/measured_parameters.md`), бэклог, UI (`requirements/ui_requirements.md` v0.2), BPMN (`diagrams/…`).
**Термины** — строго по `02_glossary.md`.

## 1. Соглашение об ID (точка состыковки I-4)

- `FR-xx` — функциональный блок; `FR-xx.y` — детальное требование внутри блока.
- В каждом требовании: формулировка + источник (UC / NFR / LGL / KPI) в скобках; приоритет унаследован от блока, если не указано иное.
- Ссылка `US-xx → FR-xx` строится ведущим в бэклоге; IDs передаются на Gate 3 (I-9).
- Числовые значения guardrails (10 алертов/час, ≤ 60 запросов/мин) и KPI-пороги — предварительные допущения, подтверждаются с заказчиком.

### FR-01. Привязка телеметрии к партиям

- **FR-01.1** При появлении новой партии в «БИТ.Лаборатории» (чтение по OData) система регистрирует начало наблюдения за партией — не позднее 5 минут с момента чтения записи партии (допущение, уточняется с заказчиком). (UC1, FR-15)
- **FR-01.2** Система связывает временные ряды телеметрии (TEL-01…TEL-13) с идентификатором партии с момента начала наблюдения; связка сохраняется на весь жизненный цикл партии. (UC1, FR-02)
- **FR-01.3** Данные, поступившие из буфера шлюза после восстановления связи (NFR-2), привязываются к партии по времени отбора отметок — без дублей и потери порядка. (NFR-2)
- **FR-01.4** При попытке закрытия партии в 1С с непроверенными предиктивными инцидентами система записывает в 1С статус/комментарий «закрытие блокировано до проверки инцидентов»; после перевода всех инцидентов в [Закрыт / Отклонён] блокировка снимается автоматически. (UC1 шаг 4, FR-06)
- **FR-01.5** Каждая проба, инцидент и задача, связанные с партией, содержат ссылку на её идентификатор (прослеживаемость; LGL-08 при применимости). (UC4, LGL-08)

### FR-02. Приём телеметрии

- **FR-02.1** Система принимает показания по TEL-01…TEL-13 (`requirements/measured_parameters.md`) по протоколам OPC-UA и MQTT с частотой не реже 1 показания/мин на параметр. (NFR-3)
- **FR-02.2** Приёмник телеметрии — отдельный сервис AquaPredict (IoT-шлюз → приёмник); приёмник не является ПЛК/SCADA, записи управляющих команд в ПЛК/SCADA запрещены. (NFR-7)
- **FR-02.3** При потере связи с центральным сервером шлюз буферизует данные до 2 часов с последующей автоматической синхронизацией в исходном порядке. (NFR-2)
- **FR-02.4** Система контролирует качество потока: пропуски отметок, «замороженные» значения (отсутствие изменения N минут — порог конфигурируемый), выход за физически возможный диапазон параметра; события качества передаются в мониторинг канала (FR-16) и помечают достоверность данных для скоринга. (FR-16, NFR-2)
- **FR-02.5** Принятые ряды хранятся с привязкой к партии и меткам времени источника; срок хранения — по LGL-06 (конкретные сроки — открытый вопрос, зона ведущего/заказчика). (LGL-06)

### FR-03. Риск-скоринг Слой 1 (rule-based)

- **FR-03.1** Слой 1 вычисляет риск по жёстким правилам телеметрии для целевых показателей из `kpi.md` §3: ОМЧ (LAB-01) — правила по температуре (TEL-07/08), озону (TEL-05), мутности (TEL-06); стартовая комплектация правил — гипотеза, уточняется ML-инженером. (UC2, kpi §3)
- **FR-03.2** Правила стартуют без размеченных данных (доступны с Этапа 0/1); Recall на Слое 1 не нормируется, акцент — Precision/FPR. (kpi §2)
- **FR-03.3** Правила ведутся в справочнике правил (условие, параметр TEL-код, порог, рекомендованное действие); изменение правила — только администратором с записью в аудит-лог. (LGL-03)
- **FR-03.4** Результат срабатывания правила — расчёт уровня риска, передаваемый в контур алертинга (FR-05) с признаком источника «Слой 1 (правило)». (UC2)

### FR-04. Риск-скоринг Слой 2 (ML) и Shadow Mode

- **FR-04.1** Слой 2 (ML-модель) вычисляет вероятность риска отклонения по целевым показателям с горизонтом ≥ 2 ч (kpi §2). (UC2, kpi §2)
- **FR-04.2** До перевода в режим советника (Advisor) ML-прогнозы не показываются персоналу (Shadow Mode): система накапливает прогнозы и метрики точности для сравнения с Baseline и Слоем 1. (UC7 шаг 4, `10_cold_start_and_archival_data.md` §4)
- **FR-04.3** Переключение Слоя 2 в Advisor — по утверждённым критериям перехода (Recall ≥ 0,75 при FPR ≤ 0,10; ≥ 4 недель стабильности; ≥ N подтверждённых инцидентов); решение фиксируется в журнале версий. (`10_…` §4, kpi §6)
- **FR-04.4** При недостатке архивных данных для обучения используется Pre-training на синтетических данных цифрового двойника (альтернативный поток 7а) с продлением периода калибровки. (UC7 поток 7а)
- **FR-04.5** Развёрнутая ML-модель мониторится на дрейф (Data Drift); при деградации — откат на предыдущую версию/Слой 1 и уведомление DS и ГТ. (LGL-13, UC6 поток 6а)

### FR-05. Предиктивные алерты и уведомления

- **FR-05.1** При превышении уровня риска системой генерируется событие `RiskAlert` с обязательными атрибутами: `партия_id`, `параметр_риска` (TEL-код), `риск_скор`, `рекомендуемое_действие`, `горизонт`, `источник` (Слой 1/2). (UC2, NFR-1)
- **FR-05.2** Latency «показание датчика → алерт» ≤ 5 секунд. (NFR-1)
- **FR-05.3** Порог критического алерта — **текущее значение рабочей точки** (конфигурируемый параметр, утверждается эксплуатантом, LGL-09); поведение при критическом уровне — по NFR-4 (красное выделение, звук, явное подтверждение ознакомления). (NFR-4, LGL-09)
- **FR-05.4** Бюджет алертов: не более 10 алертов/час на линию; при превышении — приоритизация по уровню риска и подавление дублей с сохранением признака «подавлено как дубль». (NFR-5)
- **FR-05.5** Каналы уведомлений: главный технолог — push и SMS (каналы AquaPredict); лаборант — только штатные механизмы 1С (задание создаётся в 1С; канал — открытый вопрос 1). (UC2, UC4)
- **FR-05.6** Каждое уведомление содержит глубокую ссылку на связанный объект (алерт → карточка инцидента SCR-02; задание → SCR-03) и историю доставки. (UI `requirements/ui_requirements.md` SCR-12)

### FR-06. Предиктивные инциденты, корректирующие действия (КА) и вердикты

- **FR-06.1** По алерту система создаёт запись «Предиктивный инцидент» с атрибутами (партия, параметр, риск-скор, горизонт, рекомендация, источник) и статусами: Новый → В работе → Закрыт / Отклонён. (UC2)
- **FR-06.2** Закрытие партии блокируется при наличии инцидентов в статусах [Новый / В работе] (FR-01.4). (UC1, FR-01)
- **FR-06.3** Задача «Корректирующее действие» создаётся системой в «БИТ.Лаборатории» через HTTP-сервис с рекомендованными шагами, ссылкой на инцидент и приоритетом; назначение исполнителя — в 1С. (UC3, LGL-10)
- **FR-06.4** Персонал физически выполняет действие и работает с задачей в 1С (назначение, закрытие с приложениями: фото, комментарий); статусы синхронизируются обратно в систему; время выполнения и исполнитель фиксируются. (UC3, LGL-10)
- **FR-06.5** Разделение сущностей (устранение дефекта US-05.1):
  - **результат КА** — [Выполнено / Отменено] по задаче в 1С;
  - **вердикт по инциденту** — отдельная сущность [Подтверждён / Ложное срабатывание] с указанием причины из справочника причин; хранится в системе. (FR-12)
- **FR-06.6** При результате КА [Отменено] инцидент возвращается главному технологу на пересмотр (новая рекомендация или вердикт [Ложное срабатывание]). (UC3)
- **FR-06.7** HITL-разграничение: система рекомендует, решение и физическое действие — за персоналом (дисклеймер в UI, LGL-04); ML-алерт не является основанием для браковки партии — решение только по лабораторному контролю и ЭП (LGL-11). (LGL-04, LGL-11)

### FR-07. Внеплановый (триггерный) отбор пробы

- **FR-07.1** При высоком риске отклонения система генерирует задание «Внеплановый отбор пробы» для конкретной партии с приоритетом «Срочно» и записывает его в 1С через HTTP-сервис (атрибуты: партия, инцидент-источник, параметр риска, рекомендация по точке/времени отбора). (UC4)
- **FR-07.2** Уведомление лаборанту — штатными средствами 1С; AquaPredict канал лаборанта не дублирует. (UC4, открытый вопрос 1)
- **FR-07.3** Факт отбора подтверждается сканированием штрихкода пробы в 1С; статус задания читается системой обратно; далее — стандартный лабораторный анализ. (UC4)
- **FR-07.4** Chain of Custody ведёт 1С; AquaPredict сохраняет ссылку «инцидент → задание → проба» и не содержит собственного журнала проб. (UC4, FR-08)
- **FR-07.5** Проба автоматически связывается со срезом телеметрии за окно (2 ч) до отбора — источник ground truth для обучения (FR-08.4, FR-11). (UC4, UC6)

### FR-08. Лабораторные данные: чтение из 1С и связка с телеметрией

- **FR-08.1** Система читает по OData: пробы, результаты по LAB-01…LAB-16, протоколы испытаний и их статусы валидации. (UC5, FR-15)
- **FR-08.2** Журнал проб и ввод результатов в AquaPredict отсутствуют (двойной ввод исключён, вариант A); интерфейсы ввода не предоставляются. (FR-15, UI-06)
- **FR-08.3** Сверка результатов с нормативами СанПиН 1.2.3685-21 / ГОСТ 32220-2013 из справочника нормативов — для подсветки и аналитики (информационная); решение о несоответствии остаётся в контуре 1С/лаборатории. (LGL-11)
- **FR-08.4** Автоматическая связка «проба → срез телеметрии за окно (2 ч)» выполняется для каждой пробы и фиксируется как обучающий пример (Feature Vector + метка). (UC6, FR-11)
- **FR-08.5** Статусы протоколов (валидация, ЭП, выгрузка) читаются и отображаются read-only (SCR-04/SCR-05). (UC5)

### FR-09. Данные, готовые для выгрузки во ФГИС, и статус выгрузки

- **FR-09.1** AquaPredict не выгружает протоколы во ФГИС и не подписывает их: выгрузка и ЭП — в контуре 1С/лаборатории (доработки 1С — вне проекта). (`legal/…` §F, ASM-09, вариант A)
- **FR-09.2** Система передаёт в 1С сопроводительные данные, связанные с инцидентом (срез телеметрии, инциденты, КА), — состав по согласованию с ведущим и администратором 1С (открытый вопрос 2). (UC5, вариант A)
- **FR-09.3** Система читает и отображает статус ФГИС-выгрузки и UUID зарегистрированной записи (LGL-01 в переформулированной трактовке — ожидается запись ведущего). (UC5, LGL-01)
- **FR-09.4** Повторная отправка при отказе ФГИС выполняется в контуре 1С; ошибки выгрузки отображаются системе информационно (SCR-05). (LGL-07)

### FR-10. Cold Start: ETL архива и Baseline-профиль

- **FR-10.1** Система выполняет импорт архивных данных: логи SCADA Historian (CSV / OPC-UA HDA) и структурированные лабораторные журналы; по завершении — отчёт о качестве импорта (объём, ошибки форматов, отброшенные записи). (UC7)
- **FR-10.2** Система выполняет матчинг «срез телеметрии за окно (2 ч) → проба из журнала»; отчёт о матчинге включает долю успешных сопоставлений (целевая ≥ 90 % — `kpi.md` §4) и список несопоставленных проб с причинами; повторный запуск на подмножестве поддерживается. (UC7, kpi §4)
- **FR-10.3** Система обучает Baseline-профиль (Anomaly Detection) без размеченных примеров брака; профиль имеет статус [Черновик] до подтверждения главным технологом как «Эталонный» (действие фиксируется в аудите). (UC7)
- **FR-10.4** После подтверждения профиля система работает в Shadow Mode (FR-04.2) до выполнения критериев перехода (`10_…` §4). (UC7)
- **FR-10.5** При недостатке архивных данных мастер Cold Start предлагает Pre-training на синтетике цифрового двойника с явным продлением периода калибровки (поток 7а). (UC7)

### FR-11. MLOps: разметка, переобучение, карантин конфликтов

- **FR-11.1** Система автоматически агрегирует обучающие примеры: Feature Vector (срез датчиков) + метка; **Приоритет источника разметки**: лабораторный протокол приоритетнее вердикта технолога (прокси-метка). (UC6, FR-12)
- **FR-11.2** При конфликте источников разметки или противоречии объективным данным пример помещается в карантин «Конфликт разметки» и **не используется в обучении** до разрешения (поток 6б); разрешение — выбор приоритетного источника с фиксацией решения в аудите. (UC6)
- **FR-11.3** Переобучение (Retraining) инициируется Data Scientist'ом на накопленном датасете; система выполняет пайплайн обучения и вычисляет метрики новой версии (цели по слоям — `kpi.md` §2). (UC6)
- **FR-11.4** Система сравнивает метрики новой версии с рабочей; утверждение и развёртывание — действие DS («Утвердить и развернуть»), старая версия — в архив; журнал версий ведётся. (UC6)
- **FR-11.5** При ухудшении метрик (Data Drift, поток 6а) развёртывание отменяется, датасет помечается «Требуется проверка аномалий», уведомляются DS и главный технолог. (UC6, LGL-13)
- **FR-11.6** Мониторинг дрейфа выполняется непрерывно (не только при переобучении); деградация отражается на экране «Метрики модели» (SCR-06). (LGL-13)

### FR-12. Обратная связь от эксперта (Expert Feedback Loop)

- **FR-12.1** Система фиксирует вердикт по алерту/инциденту: [Подтверждён / Ложное срабатывание] с указанием причины (поток 3а UC2). (UC2)
- **FR-12.2** Вердикт технолога — прокси-метка с приоритетом ниже лабораторного протокола (FR-11.1); при расхождении с лабораторными данными пример уходит в карантин (FR-11.2). (UC6)
- **FR-12.3** Вердикт фиксируется в веб-консоли (SCR-02) или через 1С с последующей синхронизацией; данные вердиктов направляются в обучающую выборку. (UC6)

### FR-13. Экран «Метрики модели»: KPI по слоям и рабочая точка

- **FR-13.1** Экран отображает цели по слоям и текущие значения Recall / Precision / FPR / FNR / F1, горизонт (Lead time), потребление бюджета алертов и Baseline-метрики (`kpi.md` §2–§3) — точка состыковки I-10. (kpi)
- **FR-13.2** Экран отображает рабочую точку: порог алертинга, принятые остаточные FPR/FNR, признак «утверждено эксплуатантом» и дату утверждения (LGL-09); изменение порога выполняется только в администрировании (SCR-11). (LGL-09)
- **FR-13.3** Отображается состояние модели (Shadow / Advisor / Production) и история изменений метрик/дрейфа. (kpi, FR-11)

### FR-14. Безопасность, RBAC, ПДн, аудит-лог, выборочный контроль

- **FR-14.1** Ролевой доступ (RBAC) для ролей: главный технолог, оператор линии, лаборант, руководитель лаборатории, ML-инженер, администратор, инженер КИПиА; матрица прав по экранам — `requirements/ui_requirements.md` §3. (LGL-05)
- **FR-14.2** Минимизация ПДн сотрудников: обработка только необходимых данных, маскирование в представлениях по умолчанию, раскрытие — по праву с фиксацией; основание и сроки обработки — по LGL-05/LGL-06 (сроки — открытый вопрос). (LGL-05, LGL-06)
- **FR-14.3** Аудит-лог: неизменяемый (только добавление), записи различают «рекомендация системы» / «решение человека» / «фактическое действие» и источник события (AquaPredict / 1С). (LGL-03, LGL-10)
- **FR-14.4** Периодический выборочный контроль решений персонала против automation bias: выборка подтверждённых алертов/закрытых инцидентов для проверки РЛ, отчёт о результатах; периодичность — параметр конфигурации. (LGL-14)
- **FR-14.5** Выгрузка журнала аудита (CSV) — право РЛ/АДМ, сама выгрузка фиксируется в журнале. (LGL-14)

### FR-15. Интеграция с «БИТ.Лаборатория»

- **FR-15.1** Чтение по OData: партии, пробы, результаты (LAB-01…16), планы отбора, статусы протоколов и ФГИС-выгрузки. (`02_glossary.md` §7, UC1, UC5)
- **FR-15.2** Запись через HTTP-сервис: задачи (внеплановый отбор, КА), рекомендации, вердикты, статусы/комментарии блокировки закрытия партии. (`02_glossary.md` §7, FR-06, FR-07)
- **FR-15.3** Ограничение ≤ 60 запросов/мин к 1С: пакетирование, очередь, повторные попытки с экспоненциальной задержкой; состояние очереди мониторится (SCR-11). (NFR-6)
- **FR-15.4** Настройка HTTP-сервисов и OData на стороне 1С — ответственность администратора 1С заказчика (роль в карте стейкхолдеров — ожидается от ведущего, G-3 ревью); контракты обмена версионируются. (NFR-6)
- **FR-15.5** Недоступность 1С не блокирует приём телеметрии и скоринг: данные буферизуются/ставятся в очередь; в UI — индикатор деградации (UI-08, ST-07). (NFR-6)

### FR-16. Мониторинг канала телеметрии (UC8, для инженера КИПиА)

- **FR-16.1** Система отслеживает статус подключения каждого датчика TEL-01…TEL-13: [Норма / Нет данных / «Заморожено» / Вне физического диапазона / Задержка потока] с временем последней валидной отметки. (FR-02.4, `03_stakeholder_map.md`)
- **FR-16.2** Система отображает статус буфера IoT-шлюза: заполнение, режим буферизации, оценка глубины (до 2 ч, NFR-2), прогресс автосинхронизации после восстановления связи. (NFR-2)
- **FR-16.3** О деградации канала система уведомляет инженера КИПиА (каналы — SCR-12); события качества потока доступны с историей (SCR-09). (FR-16, NFR-2)
- **FR-16.4** Инциденты и алерты, рассчитанные по данным деградировавшего канала, помечаются признаком пониженной достоверности на SCR-01/SCR-02. (FR-02.4)

## 6. Открытые вопросы (уточняются с ведущим/заказчиком)
