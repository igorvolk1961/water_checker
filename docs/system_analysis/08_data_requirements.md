# AquaPredict LIMS — Требования к данным (Data Requirements)

Раздел описывает, откуда система берёт данные для обучения ML-модели и как решается проблема холодного старта (Cold Start Problem).

## 1. Миграция исторических данных (Historical Data Backfill)

Завод не начинает работу с нуля: на производстве годами работают SCADA-системы, которые пишут логи датчиков (Historian), а лаборатория ведёт журналы. Этот механизм реализует стратегию холодного старта (см. артефакт «Холодный старт и обработка архивных данных»).

- **Требование.** Система должна предоставлять модуль ETL (Extract, Transform, Load) для импорта исторических временных рядов из SCADA-историанов (форматы CSV, OPC-UA HDA) и структурированных лабораторных журналов.
- **Требование.** Система должна поддерживать алгоритм автоматического матчинга (сопоставления) временных меток: находить срез показаний датчиков за 2 часа до времени, указанного в бумажном/Excel-журнале лаборатории.

## 2. Обучение профиля нормального состояния (Baseline Training)

Данных о «браке» может быть мало, но данных о «нормальной работе» — миллионы строк.

- **Требование.** Система должна поддерживать обучение Baseline-профиля нормального состояния методами неконтролируемого обучения (Anomaly Detection / Unsupervised Learning), не требующими размеченных данных о браке.
- **Сценарий.** Система собирает данные в течение 30 дней без генерации алертов, вычисляет многомерные границы нормы, и технолог подтверждает этот профиль как «Эталонный».

## 3. Синтетические данные (Digital Twin)

Если физических данных о поломке (например, мембраны) нет, используются физические/гидродинамические модели для генерации данных датчиков.

- **Требование.** Система должна поддерживать импорт синтетических датасетов (в формате Parquet/JSON) из внешних систем физического моделирования для первоначального обучения (Pre-training) модели.

## 4. Данные для разметки и дообучения

- **Требование.** Система должна автоматически формировать размеченные примеры (Labeled Data) путём связывания среза телеметрии (Feature Vector) с целевой переменной (Ground Truth / Label).
- **Требование (приоритет источника разметки).** При определении метки приоритет имеет объективный протокол лабораторного анализа; вердикт технолога используется как прокси-метка только при отсутствии лабораторного подтверждения.
- **Требование (шум разметки).** Система должна поддерживать статус разметки обучающих примеров (Автоматически / Проверено Data Scientist / Конфликт) и изолировать конфликтные примеры (карантин) до разрешения Data Scientist-ом.
- **Требование.** Обучающие примеры с неподтверждёнными прокси-метками (только вердикт технолога без лабораторного подтверждения) не должны использоваться для финального обучения до верификации; допускается их учёт с пониженным весом (опция конфигурации).
- **Требование.** Система должна поддерживать отзыв/переразметку примеров при выявлении ошибок (в том числе ошибок вердикта технолога) и сохранять аудит изменений метки.
