# AquaPredict LIMS — Функциональные требования (Functional Requirements)

**Версия:** 0.3. **Статус:** скелет согласован — **вариант A подтверждён ведущим (Gate 1 пройден, 2026-10-12)**; детализация Волны 2 (C-02) и учёт LGL (C-06) в работе.
**Архитектурное направление — вариант A (надстройка), ПОДТВЕРЖДЁН:** AquaPredict — предиктивная надстройка над «БИТ.Лаборатория», а не самостоятельный LIMS. Партии, пробы, результаты, протоколы, задачи и ЭП живут в 1С; AquaPredict читает их по OData, пишет задачи/рекомендации через HTTP-сервис и добавляет предиктивный контур. Принято парой по итогам ревью от 2026-10-12 (устранение противоречия Vision ↔ глоссарий §7 / NFR-6 / EPIC-01); подтверждено ведущим 2026-10-12. **Ожидается от ведущего (его зона):** правка In-Scope в `01_vision_and_scope.md`, пересмотр UC5, backfill `change_log.md`, переформулировка LGL-01 (до записей документ держит формулировки как согласованные по существу).
**Основа:** базис `01…10`, LGL-01…14 (`legal/legal_risks_and_requirements.md`), KPI (`kpi.md`), NFR/guardrails (`07_nonfunctional_requirements.md`), параметры (`requirements/measured_parameters.md`), бэклог (`backlog/product_backlog.md`).
**Термины** — строго по `02_glossary.md`. Детализация (FR-xx.y, Волна 2, задачи C-02…C-06) — после согласования скелета.

## 1. Соглашение об ID (точка состыковки I-4)

- `FR-xx` — функциональный блок; `FR-xx.y` — детальное требование внутри блока (Волна 2).
- Ссылка `US-xx → FR-xx` строится ведущим в бэклоге после появления FR.
- Приоритет: Must/Should — соответствует приоритетам эпиков бэклога.

### FR-01. Привязка телеметрии к партиям

- Партии регистрируются в «БИТ.Лаборатории» и читаются по OData; AquaPredict регистрирует начало наблюдения и связывает временные ряды телеметрии с идентификатором партии (UC1).
- Возможность закрытия партии в 1С только после проверки связанных предиктивных инцидентов (см. 05_use_case_specification.md, шаг 4) — через статус/комментарий, записанный системой.

### FR-02. Приём телеметрии

- Приём показаний по TEL-01…TEL-13 (`requirements/measured_parameters.md`) по OPC-UA / MQTT с частотой не реже 1 мин (NFR-3).
- Буферизация на стороне IoT-шлюза до 2 часов при потере связи с автосинхронизацией (NFR-2); приёмник — не ПЛК/SCADA (NFR-7, Out-of-Scope управления).

### FR-03. Риск-скоринг Фаза 1 (rule-based)

- Слой 1 — жёсткие правила телеметрии (пример: давление ниже порога → алерт) по целевым показателям LAB-01/05/09; стартуют сразу, без размеченных данных.
- Фаза 1 работает с акцентом на Precision/FPR (`kpi.md` §2); Recall не нормируется (охват правил).

### FR-04. Риск-скоринг Фаза 2 (ML) и Shadow Mode

- Слой 2 — ML-модель в теневом режиме: прогнозы не показываются персоналу, накапливаются метрики точности; переключение на Advisor по критериям фаз (`10_cold_start_and_archival_data.md` §4).
- Использование синтетических данных цифрового двойника для Pre-training (при недостатке архивных данных — альтернативный поток 7а).

### FR-05. Предиктивные алерты и уведомления

- Генерация события `RiskAlert` (`партия_id`, `параметр_риска`, `вероятность`, `рекомендуемое_действие`, горизонт); Latency «датчик → алерт» ≤ 5 с (NFR-1).
- Порог критического алерта — **текущее значение рабочей точки** (конфигурируемый параметр, утверждается эксплуатантом, LGL-09); NFR-4 (> 80 %, красное выделение, звук, явное подтверждение ознакомления) описывает поведение при текущем значении.
- Уведомления главному технологу: push и SMS (каналы AquaPredict); уведомления лаборанту — через штатные механизмы 1С (задание создаётся в 1С), канал уточняется (открытый вопрос 2).
- Бюджет алертов: не более 10 алертов/час на линию; при превышении — приоритизация и подавление дублей (NFR-5, guardrail).

### FR-06. Предиктивные инциденты, корректирующие действия (КА) и вердикты

- Создание записи «Предиктивный инцидент» в AquaPredict (статусы: Новый → Закрыт / Отклонён) с блокировкой закрытия партии без проверки.
- Разделение сущностей (устраняет категориальную ошибку US-05.1):
  - **результат КА** — [Выполнено / Отменено] по задаче;
  - **вердикт по инциденту** — отдельная сущность [Подтверждён / Ложное срабатывание] с указанием причины; хранится у системы, использовается для разметки (FR-12).
- Задача «Корректирующее действие» создаётся системой в «БИТ.Лаборатории» через HTTP-сервис с рекомендованными шагами; персонал работает с задачей в 1С (создание, назначение, закрытие с приложениями — фото, комментарий); статусы синхронизируются обратно; время выполнения и исполнитель фиксируются (LGL-10).
- HITL-разграничение: система рекомендует, решение и физическое действие — за персоналом; дисклеймер в UI (LGL-04); ML-алерт не является основанием для браковки партии — решение только по лабораторному контролю и ЭП (LGL-11).

### FR-07. Внеплановый (триггерный) отбор пробы

- Автогенерация задания на внеплановый отбор для конкретной партии с приоритетом «Срочно»: задание создаётся системой в 1С через HTTP-сервис, уведомление лаборанту — штатными средствами 1С.
- Факт отбора подтверждается сканированием штрихкода пробы в 1С; статус задания читается системой обратно; далее — стандартный лабораторный анализ; Chain of Custody ведёт 1С, AquaPredict сохраняет ссылку «инцидент → задание → проба».

### FR-08. Лабораторные данные: чтение из 1С и связка с телеметрией

- Чтение по OData: пробы, результаты по LAB-01…LAB-16, протоколы испытаний и статусы валидации; собственный журнал проб и ввод результатов в AquaPredict отсутствуют (двойной ввод исключён).
- Сверка результатов с нормативами СанПиН 1.2.3685-21 / ГОСТ 32220-2013 из справочника — для подсветки и аналитики (решение о несоответствии остаётся в контуре 1С/лаборатории, LGL-11).
- Автоматическая связка «проба → срез телеметрии за окно (2 ч)» — источник ground truth для обучения (FR-11).

### FR-09. Данные, готовые для выгрузки во ФГИС, и статус выгрузки

- AquaPredict не выгружает протоколы во ФГИС и не подписывает их: выгрузка и ЭП — в контуре 1С/лаборатории (допущение `legal/…` §F, ASM-09; доработки 1С — вне проекта).
- Система передаёт в 1С сопроводительные данные, связанные с инцидентом (телеметрия, КА), — по согласованию; читает и отображает статус выгрузки и UUID зарегистрированной записи (LGL-01 в переформулированной трактовке — уточнить с ведущим, открытый вопрос 3).

### FR-10. Cold Start: ETL архива и Baseline-профиль

- Импорт архивных данных (SCADA Historian CSV / OPC-UA HDA, лабораторные журналы), очистка и матчинг «срез телеметрии за окно (2 ч) → проба» с отчётом о качестве матчинга.
- Обучение Baseline-профиля (Anomaly Detection) и подтверждение технологом как «Эталонный»; фазы 0–3 по критериям перехода (`10_cold_start_and_archival_data.md` §4).

### FR-11. MLOps: разметка, переобучение, карантин конфликтов

- Автоагрегация обучающих примеров: Feature Vector (срез датчиков) + метка (лабораторный протокол приоритетнее вердикта технолога — Приоритет источника разметки).
- Переобучение по инициативе Data Scientist'а, сравнение метрик новой версии с рабочей, утверждение и развёртывание; отмена при ухудшении (Data Drift).
- Конфликт разметки → карантин, пример не используется в обучении до разрешения (поток 6б); мониторинг дрейфа как обязанность (LGL-13).

### FR-12. Обратная связь от эксперта (Expert Feedback Loop)

- Механизм подтверждения корректности алерта или пометки «Ложное срабатывание» с указанием причины (поток 3а UC2); вердикт — прокси-метка с приоритетом ниже лабораторного протокола.
- Данные вердиктов направляются в обучающую выборку (связка с FR-11); вердикты могут фиксироваться как в веб-консоли, так и через 1С — с последующей синхронизацией.

### FR-13. Экран «Метрики модели»

- Отображение пофазных целей и текущих значений Recall / Precision / FPR / FNR / F1, горизонта, бюджета алертов и Baseline-метрик (`kpi.md` §2–§3) — точка состыковки I-10.
- Отображение рабочей точки: порог алертинга и принятые остаточные FPR/FNR с раскрытием вероятностного характера прогноза (LGL-09); порог утверждается эксплуатантом (`legal/…` §G.2).

### FR-14. Безопасность, RBAC, ПДн, аудит-лог

- Ролевой доступ (RBAC): главный технолог, оператор линии, лаборант, руководитель лаборатории, ML-инженер; минимизация ПДн сотрудников (LGL-05, `legal/…` §I).
- Аудит-лог с различением «рекомендация системы» / «решение человека» / «фактическое действие» (LGL-10); действия, выполненные в 1С, различаются по источнику события.
- Периодический выборочный контроль решений персонала против automation bias (LGL-14).

### FR-15. Интеграция с «БИТ.Лаборатория»

- Чтение по OData: партии, пробы, результаты, планы отбора, статусы протоколов; запись через HTTP-сервис: задачи (внеплановый отбор, КА), рекомендации, вердикты (`02_glossary.md` §7).
- Ограничение ≤ 60 запросов/мин к 1С, пакетирование и очередь (NFR-6, guardrail); настройка HTTP-сервисов на стороне 1С — ответственность администратора 1С заказчика (роль отсутствует в карте стейкхолдеров — передать ведущему).

### FR-16. Мониторинг канала телеметрии (для инженера КИПиА)

- Мониторинг статуса подключения датчиков и диагностика аномалий в потоке данных (стейкхолдер из `03_stakeholder_map.md`): пропуски данных, «замороженные» значения, выход за физически возможные диапазоны.
- Статус буфера шлюза при потере связи (NFR-2); уведомления КИПиА о деградации канала — достоверность телеметрии критична для риск-скоринга (FR-03/04).

## 4. Сквозные требования, влияющие на UI (задел под C-03/C-06)

- Дисклеймеры: вероятностный характер прогноза и рабочая точка (LGL-09); HITL «система рекомендует, решает человек» (LGL-04); предупреждения против automation bias (LGL-14).
- Порог критического алерта — конфигурируемая рабочая точка (не константа); NFR-4 задаёт поведение при её текущем значении (> 80 %).
- Юридический след: ЭП и юридическая значимость протокола — в контуре 1С (LGL-02, LGL-07); AquaPredict не отображает и не хранит неподписанные протоколы как «отправляемые»; аудит различает источники шагов (LGL-10).

## 5. Открытые вопросы (уточняются в Волне 2 / с заказчиком)

1. Вид ЭП и подписант (РЛ / ГТ) — открытый вопрос 1 из `legal/…` §E; при варианте A лежит в контуре 1С.
2. Канал уведомлений лаборанту (мобильный клиент 1С, терминал на линии) — влияет на SCR-03/SCR-12.
3. Формат и объём сопроводительных данных, передаваемых в 1С для ФГИС-выгрузки (FR-09) — согласовать с ведущим и администратором 1С; переформулировка LGL-01.
4. Нужен ли оператору линии доступ в веб-консоль или только задачи в 1С (SCR-01/SCR-03).
5. Кто настраивает HTTP-сервисы и OData на стороне 1С — администратор 1С отсутствует в карте стейкхолдеров (передать ведущему, находка ревью).
