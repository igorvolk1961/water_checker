## 2. Задельные User Stories (уточняются под FR)

### EPIC-04 — Предиктивные алерты
- **US-04.1.** Как главный технолог, я хочу видеть критический алерт (риск выше настроенного порога) с рекомендацией, чтобы быстро принять решение.
  - AC: алерт содержит партия_id, показатель, риск-скор, горизонт, рекомендацию; критический уровень выделяется и требует подтверждения ознакомления (NFR-4). Порог — конфигурируемый (не константа).

### EPIC-05 — Корректирующие действия
- **US-05.1.** Как технолог, я хочу получить задачу на корректирующее действие с рекомендованными шагами и закрыть её после выполнения.
  - AC: задача создаётся автоматически из алерта; при закрытии фиксируются исполнитель, время и результат корректирующего действия [Выполнено / Отменено]. Вердикт «Ложный_алерт» относится к инциденту, а не к корректирующему действию.

### EPIC-06 — Внеплановый отбор
- **US-06.1.** Как лаборант, я хочу получить задание на внеплановый отбор по алерту с приоритетом «Срочно».
  - AC: заявка создаётся в «БИТ:LIMS» и содержит партию и показание-триггер; уведомление доставляется штатным каналом 1С/мессенджером (лаборант работает в 1С); факт отбора подтверждается сканированием штрихкода.

### EPIC-08 — Cold Start
- **US-08.1.** Как ML-инженер, я хочу импортировать архив (SCADA Historian + журналы) и обучить Baseline-профиль.
  - AC: ETL-модуль импортирует CSV/OPC-UA HDA; матчинг меток в окне 2 ч; Baseline подтверждается технологом как «Эталонный».

### EPIC-10 — MLOps / разметка
- **US-10.1.** Как ML-инженер, я хочу, чтобы примеры с конфликтом разметки уходили в карантин.
  - AC: при расхождении вердикта технолога и лабораторного результата статус = «Конфликт»; пример не используется в обучении до разрешения DS.

### EPIC-14 — Мониторинг источников телеметрии
- **US-14.1.** Как инженер КИПиА, я хочу получать диагностику по неисправным датчикам.
  - AC: система обнаруживает недоступность датчика или пропуски в потоке и формирует диагностическое уведомление; после восстановления источник возвращается в риск-скоринг.

### EPIC-01 — Интеграция с «БИТ:LIMS»
- **US-01.1.** Как система, я хочу читать партии/пробы/результаты по OData, чтобы строить прогноз по актуальным данным 1С.
  - AC: чтение партий, проб, результатов LAB-01…16, статусов протоколов/ФГИС; версионирование контракта; ≤ 60 запросов/мин.

### EPIC-02 — Сбор телеметрии
- **US-02.1.** Как система, я хочу принимать телеметрию TEL-01…13 по OPC-UA/MQTT с буферизацией, чтобы не терять данные при сбоях связи.
  - AC: частота ≥ 1/мин; буферизация до 2 ч с автосинхронизацией; привязка к партии без дублей.

### EPIC-03 — Движок риск-скоринга, Слой 1
- **US-03.1.** Как главный технолог, я хочу получать риск-оценку по правилам телеметрии, чтобы реагировать без размеченных данных.
  - AC: правила в справочнике (условие, TEL-код, порог, действие); признак источника «Слой 1»; Recall не нормируется.

### EPIC-07 — Чтение лабораторных результатов (Ground Truth)
- **US-07.1.** Как ML-инженер, я хочу получать утверждённые результаты как целевую переменную.
  - AC: чтение утверждённых результатов по OData; сверка с нормативами (информационно); read-only, без собственного журнала проб.

### EPIC-09 — Движок риск-скоринга, Слой 2 (ML)
- **US-09.1.** Как главный технолог, я хочу получать ML-прогноз риска с горизонтом ≥ 2 ч.
  - AC: ML-прогноз в Shadow Mode до выполнения критериев перехода; затем — режим советника.

### EPIC-11 — Дашборд метрик модели
- **US-11.1.** Как ML-инженер, я хочу видеть метрики по слоям и рабочую точку, чтобы контролировать качество и порог.
  - AC: Recall/Precision/FPR/FNR/F1, Baseline, бюджет алертов, рабочая точка (SCR-06); статус модели (Shadow/Advisor/Production).

### EPIC-12 — Безопасность, ПДн, ЭП, аудит
- **US-12.1.** Как руководитель лаборатории, я хочу, чтобы аудит различал «рекомендация / решение / действие», а ПДн были защищены.
  - AC: RBAC по ролям; неизменяемый аудит-лог; маскирование ПДн; экспорт аудита фиксируется.

### EPIC-13 — UI/UX-основа (веб-консоль технолога)
- **US-13.1.** Как технолог, я хочу работать в веб-консоли (SCR-01…12) с дисклеймерами HITL и рабочей точки.
  - AC: навигация SCR-01 → SCR-02 → SCR-03; дисклеймеры (LGL-04, LGL-09); критические алерты выделяются (NFR-4).
- **US-13.2.** Как главный технолог, я хочу пометить алерт как ложное срабатывание с указанием причины, чтобы система не повторяла ошибку.
  - AC: вердикт инцидента фиксируется как отдельная аудируемая запись (значение [Ложное срабатывание], причина из справочника, автор, дата); данные вердикта уходят в обучающую выборку (FR-12.1/12.3).

## 3. Правила

- **Definition of Ready:** есть источник (UC/NFR/LGL), приоритет, зависимости, критерии приёмки.
- **Definition of Done:** реализовано, покрыто приёмочными критериями, не противоречит базису 01–10.
- **Приоритизация:** сначала Must-цепочка UC1→UC2→UC3/UC4 (UC5 — чтение утверждённых результатов, EPIC-07); платформенные (EPIC-12) идут сквозным потоком.
- **Упаковка:** UC — источник истины; User Story — упаковка, Acceptance Criteria UC не дублируют (см. `roadmap_and_plan.md`, §8).
