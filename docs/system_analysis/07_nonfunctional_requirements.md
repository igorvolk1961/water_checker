# AquaPredict LIMS — Нефункциональные требования (NFR)

Для IoT/ML-систем нефункциональные требования критически важны и показывают зрелость аналитика.

1. **Производительность (Performance).** Задержка (latency) между получением данных с датчика и генерацией предиктивного алерта не должна превышать 5 секунд.
2. **Надёжность (Reliability).** Система должна поддерживать буферизацию данных с датчиков на стороне шлюза в течение до 2 часов при потере связи с центральным сервером, с последующей автоматической синхронизацией.
3. **Интегрируемость (Interoperability).** Система должна поддерживать приём данных по стандартным промышленным протоколам OPC-UA и MQTT.
4. **Удобство использования (Usability).** Критическое предупреждение (уровень риска выше настроенного **порога алертинга / рабочей точки**) должно визуально выделяться на дашборде технолога (красный цвет, звуковой сигнал) и требовать явного подтверждения ознакомления. Порог — конфигурируемый параметр (не константа).

## Guardrails (ограничения-предохранители)

5. **Бюджет алертов (Alert Budget).** Система не должна генерировать более **10 алертов в час** на линию; при превышении — приоритизация и подавление дублей (защита от alert fatigue и снижения доверия технолога). **Порядок:** подавление дублей выполняется до создания предиктивного инцидента — подавленный дубль инцидент не создаёт (решение В-6). Связано с FPR (`kpi.md`).
6. **Нагрузка на «БИТ:LIMS» (1С).** Обмен через OData/HTTP не должен превышать **≤ 60 запросов в минуту** к серверу 1С; пиковые операции — пакетирование и очередь запросов. Согласуется с администратором 1С.
7. **Отсутствие обратного управления.** Система не пишет команды в ПЛК/SCADA (Out-of-Scope); любые записи — только в «БИТ:LIMS» (задачи, комментарии, статусы через штатные сервисы).

> Значения guardrails (10 алертов/час, ≤ 60 запросов/мин) — предварительные допущения, подтверждаются с заказчиком и владельцем 1С.

## Безопасность, отказоустойчивость, время (дополнение по ревью)

8. **Аутентификация веб-консоли.** Доступ только после аутентификации: интеграция с каталогом заказчика (AD/LDAP) при наличии, иначе — локальные учётные записи; сессии с истечением, блокировка после N неудачных попыток. Роли — по RBAC (FR-14.1).

9. **Транспортная безопасность.** Все внешние каналы — защищённые: HTTPS/TLS для OData/HTTP к «БИТ:LIMS», TLS для MQTT, шифрование трафика датчиков/шлюза; проверка сертификатов сервера.

10. **Отказоустойчивость и резервное копирование.** Целевые показатели: **RPO ≤ 15 мин**, **RTO ≤ 4 ч** (допущения, уточняются с заказчиком); регулярное резервное копирование БД и конфигурации; восстановление проверяется. Доступность — не ниже 99 % (см. §4 SLA-допущение).

11. **Синхронизация времени.** NTP на всех узлах (шлюз, серверы); корректность меток времени — основа сопоставления «срез телеметрии → проба» (связано с FR-02.6).
