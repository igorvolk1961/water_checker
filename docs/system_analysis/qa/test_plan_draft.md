# Тест-план проекта AquaPredict (черновик, каркас)

**Версия:** 0.1-каркас (2026-10-13). **Автор:** коллега. **Статус:** на назначение ответственных и заполнение — тестировщик в смете есть (`cost_estimation.md` §3, 300 ч), в плане реализации задачи тестирования не распределены (находка сеньор-ревью №2, передана ведущему).
**Основание:** ТЗ §5.7 («программа и методика испытаний» — обязательный документ поставки), §7.2 (порядок приёмки), NFR-1…7, `ui_requirements.md`.

## 1. Объект и цели

- Объект: Система AquaPredict (вариант A — надстройка над «БИТ.Лаборатория»).
- Цели: подтвердить выполнение FR-xx.y и NFR; проверить guardrails (≤ 10 алертов/час, ≤ 60 запросов/мин, отсутствие команд в ПЛК/SCADA); подготовить доказательства для актов этапов R0–R2.

## 2. Уровни и виды тестирования

| Вид | Что проверяет | Когда | Основа |
| --- | --- | --- | --- |
| Модульное | юнит-тесты backend/frontend (pytest — стек) | непрерывно, R0+ | код, EPIC-задачи |
| Интеграционное | стыки: шлюз → приёмник → скоринг; HTTP-сервис → 1С | R0 | BPMN UC1/UC2 |
| **Контрактное (1С)** | соответствие OData/HTTP контракту обмена; идемпотентность записи (FR-15.6); поведение при ошибках и ретраях | R0 | контракт обмена (В-7.3) |
| Сквозное (E2E) | UC2 → UC3 → UC4 по BPMN, замыкание golden standard (UC6) | R1 | BPMN, sequence-диаграммы |
| Нагрузочное | NFR-1 latency ≤ 5 с; NFR-6 ≤ 60 запросов/мин; NFR-5 бюджет алертов | R1–R2 | NFR, `kpi.md` §4 |
| Безопасность и ПДн | RBAC-матрица (все роли × экраны), маскирование ПДн, аудит-различение источников | R1 (EPIC-12) | FR-14, LGL-03/05/10 |
| Валидация ПО | по ГОСТ ISO/IEC 17025-2019 — подтверждение пригодности для назначения | R2 (приёмка) | ТЗ §7.2, LGL-R6 |
| UI-приёмка | поэкранные чек-листы SCR-01…12 (`qa/acceptance_checklists_scr.md`) | каждый этап | `ui_requirements.md` v0.3 |

## 3. Тестовое окружение (⚠️ критическая зависимость)

- **Симулятор датчиков:** генератор телеметрии по TEL-01…13 со сценариями: норма / плавный дрейф / резкая аномалия / потеря связи (проверка буфера NFR-2) / недостоверные данные (FR-02.4). **В плане R0 не запланирован — предложено ведущему добавить (зона backend).**
- **Мок-1С:** заглушка OData (партии, пробы, результаты, статусы) и HTTP-сервиса (задачи, вердикты) с управляемыми задержками и ошибками — для контрактного тестирования без боевого 1С.
- Dev/Test/Prod окружения — `plans/backlog_implementation_plan.md` §5.

## 4. Критерии

- Начало этапа тестирования: сборка развёрнута на Test, смоук пройден.
- Готовность к акту: 100 % критических чек-листов этапа пройдено, 0 открытых критических дефектов, NFR-замеры зафиксированы в отчёте.
- Отчёт по этапу: результаты NFR-замеров + список дефектов + статус чек-листов приёмки.

## 5. Роли (требуется решение ведущего)

- Тестировщик (в смете) — исполнение.
- Коллега — чек-листы UI-приёмки, поддержка ПМИ.
- Ведущий — контрактное тестирование 1С, окружение.
