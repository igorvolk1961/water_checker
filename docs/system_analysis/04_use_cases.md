# AquaPredict LIMS — Варианты использования (Use Cases)

Перечень ключевых сценариев, отличающих систему от обычной LIMS. Формулировки UC3–UC5 уточнены так, чтобы не противоречить границе проекта «Прямое автоматическое управление оборудованием — Out-of-Scope»: система управляет бизнес-процессом и документооборотом, а не физическим оборудованием.

## Сводный перечень

| Код | Название | Акторы |
| --- | --- | --- |
| UC1 | Регистрация производственной партии и привязка к потоку данных датчиков | Главный технолог / Система |
| UC2 | Получение и обработка предиктивного предупреждения | Главный технолог, ML-Модуль |
| UC3 | Регистрация и контроль выполнения корректирующего действия (КА) | Главный технолог, Оператор линии |
| UC4 | Формирование задания на внеплановый (триггерный) отбор пробы | Лаборант, ML-Модуль |
| UC5 | Валидация и экспорт протокола испытаний во ФГИС Росаккредитации | Лаборант, Руководитель лаборатории |
| UC6 | Валидация прогноза и пополнение обучающей выборки | ML-инженер (Data Scientist), Система |

## UC1. Регистрация производственной партии и привязка к потоку данных датчиков

Инициация наблюдения за новой партией: система регистрирует партию и начинает связывать временные ряды телеметрии с её идентификатором.

## UC2. Получение и обработка предиктивного предупреждения

**Основной дифференциатор системы.** ML-модуль рассчитывает вероятность риска, система создаёт предиктивный инцидент и уведомляет технолога. Детальная спецификация — в отдельном артефакте «Спецификация варианта использования».

## UC3. Регистрация и контроль выполнения корректирующего действия (КА)

- **Суть.** Система не выполняет действие сама. Она создаёт цифровую задачу (тикет) для персонала и фиксирует факт его выполнения.
- **Основной поток:**
  1. При получении предиктивного алерта (UC2) система автоматически создаёт задачу «Корректирующее действие» с рекомендованными шагами (например, «Проверить давление на фильтре №2, при необходимости промыть»).
  2. Задача назначается главному технологу или оператору линии (с уведомлением в мессенджер / на пульт).
  3. **Персонал физически выполняет действие на оборудовании** (это происходит вне системы).
  4. Персонал заходит в систему, открывает задачу и нажимает «Действие выполнено», при необходимости прикрепляя фото или комментарий.
  5. Система фиксирует время выполнения, закрывает задачу и снимает блокировку с производственной партии.
- **Почему это в In-Scope:** система управляет бизнес-процессом и документооборотом, а не физическим оборудованием.

## UC4. Формирование задания на внеплановый (триггерный) отбор пробы

- **Суть.** Система не управляет роботом-сэмплером. Она инициирует рабочий процесс для живого лаборанта.
- **Основной поток:**
  1. ML-модуль фиксирует высокий риск отклонения (например, рост мутности).
  2. Система автоматически генерирует заявку в модуль LIMS на «Внеплановый отбор пробы» для конкретной производственной партии, указывая приоритет «Срочно».
  3. Лаборант получает уведомление на планшет/терминал.
  4. **Лаборант физически идёт к линии, отбирает пробу в стерильную тару, маркирует её и приносит в лабораторию.**
  5. Лаборант сканирует штрихкод пробы в системе, подтверждая факт отбора, и далее выполняет стандартный лабораторный анализ.
- **Почему это в In-Scope:** система управляет маршрутизацией задачи и прослеживаемостью (Chain of Custody), физический отбор остаётся за человеком.

## UC5. Валидация и экспорт протокола испытаний во ФГИС Росаккредитации

- **Суть.** Чисто информационный процесс, не затрагивающий производственное оборудование.
- **Основной поток:**
  1. Лаборант вносит результаты анализов (или они автоматически загружаются из прибора).
  2. Система автоматически сверяет результаты с актуальными нормативами СанПиН (из справочника).
  3. Руководитель лаборатории (или система, если настроено авто-подписание) валидирует протокол.
  4. Система формирует XML-файл в строгом формате, требуемом ФГИС Росаккредитации, и отправляет его через защищённый API-шлюз.
  5. Система получает и сохраняет идентификатор (UUID) зарегистрированной записи из ФГИС.
- **Почему это в In-Scope:** это обмен данными между информационными системами, физическое оборудование не задействовано.

## UC6. Валидация прогноза и пополнение обучающей выборки

Описывает, как система превращает результаты повседневной работы в данные для обучения ML.

- **Основной актер:** ML-инженер (Data Scientist).
- **Вторичный актер:** Система (автоматический фоновый процесс).
- **Предусловие:** в системе накопились новые данные — исторические показания датчиков и фактические результаты лабораторных анализов (или вердикты технологов) по ним.
- **Основной поток:**
  1. Система автоматически агрегирует «сырые» данные: связывает временной интервал показаний датчиков (например, за 2 часа до отбора пробы) с фактическим результатом лабораторного анализа этой пробы или с вердиктом технолога по инциденту.
  2. Система помечает эти связанные данные как «Размеченный пример» (Labeled Data), где показания датчиков — это признаки (features), а результат лаборатории/технолога — целевая переменная (ground truth / label).
  3. Data Scientist открывает модуль «Управление ML-моделями» и видит уведомление: «Накоплено 500 новых размеченных примеров».
  4. Data Scientist инициирует процесс переобучения (Retraining) модели на расширенном датасете.
  5. Система запускает пайплайн обучения и вычисляет метрики новой версии модели (точность, полнота, F1-score).
  6. Система сравнивает метрики новой модели с текущей рабочей версией.
  7. Если метрики улучшились (или находятся в допустимом коридоре), Data Scientist нажимает «Утвердить и развернуть».
  8. Система переводит новую версию модели в статус «Production», а старую версию отправляет в архив.
- **Альтернативный поток 6а. Ухудшение метрик (Data Drift):**
  - В шаге 6 система обнаруживает, что точность новой модели упала (например, из-за того, что на производстве заменили тип фильтра, и старые закономерности не работают).
  - Система отменяет развёртывание, помечает датасет флагом «Требуется проверка аномалий» и отправляет уведомление Data Scientist-у и главному технологу для совместного расследования причин изменения процесса.

### Связь UC2, UC4, UC5, UC6 (формирование «золотого стандарта» данных)

Система автоматически создаёт обучающие данные в процессе обычной работы:

1. **UC2 (Алерт).** ML предсказывает риск; система запоминает срез данных со всех датчиков в этот момент времени (Feature Vector).
2. **UC4 (Внеплановая проба).** Лаборант берёт пробу именно по этому алерту.
3. **UC5 (Результат).** Лаборатория выдаёт результат (например, «ОМЧ в норме» или «ОМЧ превышен»).
4. **Автоматическая связка (behind the scenes).** Система берёт Feature Vector из шага 1 и присваивает ему метку (Label) из шага 3:
   - ML предсказал риск, а лаборатория сказала «норма» → **False Positive**; кейс сохраняется, чтобы в будущем (UC6) научиться его не триггерить;
   - ML предсказал риск, и лаборатория подтвердила «превышение» → **True Positive**; кейс сохраняется, чтобы укрепить данную закономерность.

Таким образом, каждый закрытый инцидент или проведённый анализ автоматически становится новым учебным примером, делая систему точнее с каждым днём.
