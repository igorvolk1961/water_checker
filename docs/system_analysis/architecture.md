# AquaPredict — Архитектура системы (Architecture)

Документ фиксирует **архитектурный стиль**, границы контейнеров, применяемые **паттерны и обоснование их выбора** (с альтернативами), модель взаимодействия и развёртывание. Дополняет C4-диаграммы (`diagrams/c4_context.md`, `c4_containers.md`, `c4_components.md`), стек (`architecture_stack.md`) и юридическую рамку (`legal/`). Термины — по `02_glossary.md`.

## 1. Область и ограничения

- Один завод, одна линия (масштабируется на несколько); пользователи консоли — до ~20 одновременно (допущение).
- Нагрузка: 13 тегов × 1 изм./мин ≈ 18 720 записей/сутки ≈ 6,8 млн/год; latency ≤ 5 с; ≤ 60 зап./мин к 1С.
- Интеграция с внешней учётной системой «БИТ.Лаборатория» (1С) — OData/HTTP; лабораторный контур — Out-of-Scope (вариант A).
- Команда небольшая; фазовое финансирование (MVP → Advisor → Active).

## 2. Архитектурный стиль: решение и обоснование

**Выбранный стиль:** **модульный монолит (API) + выделенные воркеры (ML-воркер и воркер очереди) + общая БД PostgreSQL; Redis — очередь/кэш; развёртывание в контейнерах.** Взаимодействие с 1С изолировано отдельным сервисом синхронизации.

### Почему так

1. **Масштаб и нагрузка не требуют микросервисов.** При одном заводе и низкой частоте данных полноценные микросервисы добавляют распределённую сложность (сетевые вызовы, распределённые транзакции, трассировка, эксплуатация) без выигрыша; CAPEX/OPEX и сроки растут.
2. **Домен сильно связный.** Риск-скоринг, инциденты, задачи и разметка работают с одними и теми же сущностями (партия, инцидент, задача, пример) — единая транзакционная БД проще и надёжнее, чем согласование данных между сервисами.
3. **Разные профили ресурсов → выделяем ровно то, что отличается.** Обучение моделей и мониторинг дрейфа — периодические тяжёлые задачи; ретраи к 1С — фоновые. Их изоляция в отдельные воркеры защищает API от блокировок и сбоев, не превращая систему в «зоопарк» сервисов.
4. **Внешняя система (1С) — точка изменчивости.** Её модель данных и лимиты (≤ 60 зап./мин) изолируются сервисом синхронизации (адаптер/ACL), чтобы изменения 1С не «протекали» в домен.
5. **Путь эволюции.** Границы, намеченные C4 (API, sync, telemetry receiver, ML worker), позволяют позже выделить сервисы, если вырастет число линий/нагрузка — без переписывания домена.

### Рассмотренные альтернативы и почему отклонены

| Альтернатива | Почему отклонена |
| --- | --- |
| Полные микросервисы | Избыточная распределённая сложность и эксплуатация; сложнее согласованность; выше стоимость при малом масштабе. |
| Единый монолитный процесс без воркеров | Обучение/ретраи блокировали бы API; хуже изоляция сбоев; невозможно независимо масштабировать тяжёлые задачи. |
| Serverless (FaaS) | Нет постоянных соединений OPC-UA/MQTT; ограничения по длительности/состоянию; удельная стоимость выше при постоянной нагрузке. |
| Прямая запись в SCADA/ПЛК | Out-of-Scope (NFR-7): безопасность, сертификация, ответственность. |

**Последствия:** единая БД — единая точка масштабирования; модульный монолит требует дисциплины модулей (границы внутри API-сервера); выделенные воркеры усложняют деплой (несколько процессов).

## 3. Контейнеры и обоснование границ

См. `diagrams/c4_containers.md`. Обоснование выделения:

| Контейнер | Зачем выделен |
| --- | --- |
| **Веб-консоль** (Jinja2+HTMX, server-rendered) | Нет отдельного SPA-стека (OQ-12); отдаётся API-сервером; проще сопровождение. |
| **API-сервер** (FastAPI) | Синхронные запросы консоли и координация; stateless (сессии — в Redis/БД), масштабируется. |
| **Сервис синхронизации с 1С** | Изоляция внешней системы + rate limiting (≤ 60 зап./мин) + идемпотентность. |
| **Приёмник телеметрии** | Постоянные соединения OPC-UA/MQTT — иной профиль, чем HTTP-API. |
| **ML-воркер** | Периодические тяжёлые задачи (Baseline, обучение, дрейф) — изоляция от API. |
| **PostgreSQL** | Единый источник истины домена и телеметрии (партиционирование, retention 1 год). |
| **Redis** | Очередь исходящих записей и кэш (персистентность AOF/RDB). |

## 4. Паттерны: применение и обоснование

| Паттерн | Где | Зачем (обоснование) | Требование | Альтернатива (почему не она) |
| --- | --- | --- | --- | --- |
| **Idempotency Key** | Запись в 1С | Ретраи не должны создавать дубли задач | FR-15.6 | Дедупликация на стороне 1С — не в нашей зоне контроля |
| **Persistent Queue (Outbox-подобный)** | Исходящие записи в 1С | Не терять задачи при недоступности 1С; переживает рестарт | FR-15.5 | Синхронная запись — блокировки и потери |
| **Retry + Exponential Backoff** | Сервис синхронизации | Устойчивость к временным сбоям 1С | FR-15.3 | Фиксированные повторы — перегрузка 1С |
| **Rate Limiting (token bucket)** | Сервис синхронизации | Guardrail ≤ 60 зап./мин | NFR-6 | Без лимита — риск деградации 1С |
| **Adapter + Anti-Corruption Layer** | Интеграция 1С | Изоляция чужой модели данных/статусов | FR-15, LGL-R3 | Прямые вызовы — протечки модели 1С в домен |
| **Repository** | Доступ к БД (SQLAlchemy) | Изоляция домена от деталей хранения | — | Сырой SQL в сервисах — связность |
| **CQRS-lite (проекция)** | 1С = источник истины для лабораторного контура; AquaPredict — проекция (read) | Не дублировать лабораторный учёт; отдельные модели чтения/записи | FR-08, FR-09, вариант A | Полная двусторонняя синхронизация — конфликты и двойной ввод |
| **Server-Sent Events (SSE)** | Поток алертов в консоль | Низкая задержка, один канал на сервере | FR-05 | Polling — нагрузка и задержка; WebSocket — избыточно |
| **Shadow Deployment** | Ввод ML (теневой режим) | Безопасный rollout без влияния на пользователей; сравнение с baseline | FR-04.2, `10_*` | Прямой «прод» — риск ложных алертов |
| **Feature Store** | Признаки train/inference | Single source признаков (консистентность обучения и инференса) | FR-10/11 | Пересчёт признаков в разных местах — расхождения |
| **Partitioning + Retention** | Телеметрия в PostgreSQL | Объёмы и срок хранения | LGL-06 | TimescaleDB — доп. инфраструктура (опционально) |
| **RBAC + immutable Audit Log** | Безопасность | Юридические требования к доступу и следу | LGL-05/10 | Ручные проверки — не масштабируется |
| **Buffering on the Edge** | IoT-шлюз | Работа при потере связи до 2 ч | NFR-2 | Централизованная буферизация — потери при обрыве |
| **Backpressure** | Очередь + бюджет алертов | Защита персонала/1С от перегрузки | NFR-5/6 | Без ограничения — alert fatigue/перегрузка |
| **Health Checks / Circuit Breaker** (опц.) | Приёмник, синхронизация | Быстрое обнаружение деградации и размыкание по сбоям | NFR-10 | Без них — «зависшие» цепочки; опционально для MVP |
| **Dependency Injection** | FastAPI (`Depends`) | Тестируемость, единая конфигурация | — | Ручное создание зависимостей — связность |

## 5. Взаимодействие и данные

- **Источники истины:** 1С — лабораторный контур (партии, пробы, результаты, протоколы, задачи, ЭП, ФГИС); AquaPredict — телеметрия, риск-скор, инциденты, вердикты, аудит.
- **Согласованность:** между системами — **в конечном счёте согласованная** (idempotency + persistent queue + retry); внутри AquaPredict — транзакции PostgreSQL.
- **Чтение из 1С** — OData; **запись в 1С** — HTTP-сервис (см. `requirements/integration_contract_1c.md`).
- **События домена** (для очереди/аудита): `RiskAlert`, `IncidentCreated`, `CorrectiveActionRequested`, `VerdictRecorded`, `BatchCloseBlocked/Unblocked`, `SamplingRequested`.

## 6. Развёртывание

- Контейнеризация (Docker); окружения Dev/Test/Prod; контейнеры: `app` (API+консоль), `worker` (очередь), `ml-worker`, `postgres`, `redis`.
- Презентация (GitHub Pages) и документация — вне продового контура.
- External: 1С (заказчик), IoT-шлюз/датчики (Исполнитель), push/SMS-шлюз.

## 7. Сквозные аспекты

- **Безопасность:** TLS для внешних каналов (NFR-9), RBAC (FR-14.1), аутентификация AD/LDAP (NFR-8), аудит (FR-14.3).
- **Наблюдаемость:** health-эндпоинты, метрики моделей (SCR-06), индикатор деградации синхронизации (UI-08), статус буфера шлюза (SCR-09).
- **Конфигурация:** `pydantic-settings` (env); секреты — вне репозитория.
- **Время:** NTP на всех узлах (NFR-11) — основа матчинга «срез → проба».

## 8. Архитектурные решения (ADR, кратко)

| ID | Решение | Обоснование | Альтернатива |
| --- | --- | --- | --- |
| ADR-01 | Стиль: модульный монолит + воркеры + общая БД | см. §2 | микросервисы, serverless |
| ADR-02 | Очередь исходящих — Redis (AOF) | стек «Фоновые задачи — Redis»; простая персистентность | очередь в БД, Kafka |
| ADR-03 | Idempotency-ключи записи в 1С | ретраи без дублей | дедуп на стороне 1С |
| ADR-04 | Фронтенд — Jinja2 + HTMX (server-rendered) | без node-сборки, быстро, read-only консоль | React/Vue SPA |
| ADR-05 | Ввод ML — Shadow Mode | безопасный rollout | сразу «прод» |
| ADR-06 | Вариант A — надстройка над 1С | не дублировать лабораторный контур | standalone LIMS |
